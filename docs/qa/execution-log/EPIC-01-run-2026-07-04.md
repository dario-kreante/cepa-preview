## Hallazgos

### HALLAZGO-EPIC01-01 (Critical) — Colisión de folios provoca una excepción no controlada (500 / conexión caída) tras un reingreso
- **TCs relacionados:** TC-CEPA-011-002, TC-CEPA-011-006 (descubierto incidentalmente al ejecutarlos en secuencia)
- **Pasos de reproducción:**
  1. Crear un ingreso con folio manual (ej. `F-100`) para el paciente A.
  2. Registrar un reingreso explícito (`es_reingreso: true`) del mismo paciente A al mismo folio `F-100` — el sistema lo acepta correctamente (dos filas en `ingreso` con `folio='F-100'`, mismo `paciente_id`, comportamiento esperado de RN-2/RN-3).
  3. Cualquier intento posterior de crear un ingreso que también use el folio `F-100` (un segundo reingreso legítimo del mismo paciente, o un intento de colisión de otro paciente) hace que el backend responda con un error de conexión (`net::ERR_FAILED` / conexión caída) en vez de un 200 o 409.
- **Causa raíz:** `backend/app/services/folio.py:41-45` (`folio_existe()`) usa `.scalar_one_or_none()`, que exige que exista **como máximo una fila** con ese folio. Pero un reingreso legítimo ya crea una segunda fila con el mismo folio (por diseño). En cuanto un folio acumula 2 filas, `folio_existe()` lanza `sqlalchemy.exc.MultipleResultsFound`, una excepción no controlada que tira la request (ver traceback completo en `backend/app/services/ingreso.py:57` → `folio.py:45`).
- **Impacto:** cualquier folio con más de un reingreso queda "roto": ninguna operación de creación que lo referencie vuelve a funcionar (ni un tercer reingreso legítimo, ni la detección de colisión con otro paciente). Es una condición fácil de alcanzar en el uso real (pacientes con licencias/atenciones repetidas al mismo folio son el caso de uso explícito de CEPA-011).
- **Causa adicional:** la columna `ingreso.folio` (`backend/app/models/ingreso.py:43`) no tiene una restricción `unique` a nivel de base de datos (solo `index=True`), pese a que el docstring del modelo dice "único entre ingresos distintos". La unicidad depende enteramente del chequeo aplicativo, que además está roto para el caso de reingresos múltiples.
- **Sugerencia:** cambiar `folio_existe()` para contar filas (o usar `.first()`/`exists()`) en vez de `scalar_one_or_none()`, ya que por diseño puede haber múltiples filas legítimas con el mismo folio.

### HALLAZGO-EPIC01-02 (Critical, alcance amplio) — CEPA-013, 014, 015 (captura) y 016 (captura) no tienen interfaz de usuario
- **TCs afectados directamente:** todos los Fail de CEPA-013 (7), CEPA-014 (6), y los de captura/edición de CEPA-015 (2) y CEPA-016 (4) — 19 TCs en total, más 3 adicionales de arrastre (ver notas por TC).
- El frontend (`frontend/src/features/ingresos/`) solo implementa: el formulario de alta (`AltaIngresoPage.tsx`) y la ficha de paciente de solo-consulta (`PatientSheet.tsx`, tabs Resumen/Licencias/Fármacos/Controles/Observaciones). `frontend/src/features/ingresos/hooks.ts` no tiene ningún hook para seguimiento, consentimiento, ODAs, cierre ni inicio de tratamiento — únicamente `useCrearIngreso`. Confirmado por búsqueda exhaustiva en el árbol `src/` (no hay ningún componente/diálogo con esos nombres fuera del backend).
- El backend sí implementa correctamente toda la lógica de negocio de estas 4 historias (`PUT /ingresos/{id}/seguimiento`, `/consentimiento`, `POST /cierre`, `/iniciar-tratamiento`, `POST/GET /ingresos/{id}/odas`, `GET /odas/alertas`) — verificado exhaustivamente vía API en esta corrida (ver detalle por TC). El problema es exclusivamente de frontend: no hay dónde, en la aplicación web, que un Administrativo o Coordinación registre fecha de acogida, evaluaciones médicas/psicológicas, estado del consentimiento, ODAs, o cierre/alta de un caso.
- **Excepción parcial:** el panel de Alertas (`AlertsPanel.tsx`, compartido con el resto del sistema) sí consume `GET /api/v1/alertas` y **sí muestra** correctamente "Consentimiento pendiente" y "Oda por vencer" (confirmado visualmente). Por eso los TCs que solo piden ver la alerta (015-002, 015-006, 016-003) pasan; los que piden abrir un formulario para *crear/editar* datos no.
- **Impacto:** de cara a un usuario real, un Administrativo no puede hoy registrar hitos clínicos, cerrar un caso, dar de alta a un paciente, registrar una ODA o marcar un consentimiento como firmado desde la aplicación — estas 4 historias (la mitad de EPIC-01 en cantidad de TCs) están, en la práctica, sin terminar del lado de producto aunque el backend esté listo.
- **Nota:** en cada TC de esta categoría se verificó independientemente la lógica de negocio vía API como evidencia de que, cuando se construya la UI, el backend que la soportará ya se comporta correctamente (ver detalle por TC).

### HALLAZGO-EPIC01-03 (Major) — El formulario "Nuevo ingreso" carece de varios campos del PRD §7.1.1
- **TC:** TC-CEPA-010-007
- `frontend/src/features/ingresos/AltaIngresoPage.tsx` solo renderiza: RUT, Nombre, Edad, Región, Diagnóstico, Modelo de tratamiento, Fecha de ingreso, Sexo, Tipo de derivación, Tipo de ingreso (10 campos). Faltan del formulario: **folio (manual)**, **teléfono**, **correo**, **fecha DIEP/DIAT**, **razón social / centro de trabajo**, **número de siniestro**, y el toggle de **reingreso** (`es_reingreso`) — aunque `ingresoSchema.ts` y el backend (`IngresoCreate`) sí los soportan.
- Verificado que el backend persiste y recupera estos 7 campos sin pérdida vía API (round-trip exacto). La brecha es 100% de frontend.
- **Impacto:** hoy, un Administrativo no puede cargar el teléfono/correo/razón social/fecha DIEP-DIAT de un paciente al momento del alta desde la UI; tendría que hacerlo después por otra vía (no hay una vía UI tampoco, ver HALLAZGO-EPIC01-02 relacionado — el `PATCH /pacientes/{id}` para datos de contacto tampoco tiene UI).
- **Relacionado:** esto también es la causa por la que el flujo de folio manual/reingreso (historias CEPA-011) no tiene ninguna superficie de UI — se verificó exclusivamente por API en esta corrida.

### HALLAZGO-EPIC01-04 (Major) — Sin autocompletado de paciente existente por RUT
- **TC:** TC-CEPA-010-001

### HALLAZGO-EPIC01-06 (Major) — La vista 360°/ficha del paciente no incluye la dimensión "Reintegro"
- **TC:** TC-CEPA-012-001
- La ficha de paciente (`PatientSheet.tsx`) tiene exactamente 5 tabs: Resumen, Licencias, Fármacos, Controles, Observaciones. No existe un tab "Reintegro", pese a que el AC pide explícitamente "ingresos, fármacos, licencias, controles y reintegro" en una sola pantalla.
- Curiosidad de implementación: el endpoint `GET /pacientes/{id}/vista-360` (`Vista360` schema) sí define un campo `reintegro`, pero el servicio `vista_360()` (`backend/app/services/busqueda.py`) lo devuelve **siempre como lista vacía hardcodeada** (comentario del propio código: "Otras dimensiones quedan como ranuras"), y en la práctica el frontend ni siquiera usa ese campo — trae licencias/fármacos/controles con hooks independientes por ingreso (`useLicenciasPorIngreso`, etc.), no del payload de vista-360. Es decir, el campo `reintegro` de ese endpoint es código muerto en ambos lados.
- El resto de dimensiones sí funciona correctamente: búsqueda por RUT/folio/nombre lleva al mismo paciente, y Licencias/Fármacos/Controles se muestran con conteos reales en la ficha.

A la escala actual, `GET /pacientes/{id}/vista-360` respondió consistentemente en 3–13 ms (5 mediciones), muy por debajo del objetivo de 10 s / 2 s. La consulta es un filtro simple por `paciente_id` (FK), por lo que es razonable esperar que escale, pero esto no reemplaza una prueba de carga real a volumen objetivo.
