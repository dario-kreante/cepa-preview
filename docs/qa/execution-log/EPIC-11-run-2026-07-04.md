- Frontend: Vite dev server local (`localhost:5173`, `cepa-frontend`, servidor reutilizado).

No es una limitación del sistema bajo prueba.

También se publicó un segundo formulario ("reintegro") para TC-111-005.
- PDF de prueba generado ad-hoc con `pypdf` (contenido de texto real vía content stream manual, sin dependencias externas como reportlab): `ficha_sociodemografica.pdf` con RUT, nombre, sexo, fecha de nacimiento y comuna en formato "Clave: Valor". Un segundo PDF en blanco (página sin contenido de texto) para simular el escenario de PDF escaneado sin capa de texto, y un archivo `.docx` (bytes no-PDF) para el caso de formato no soportado.
- RUT sintético usado: `15678234-3` (dígito verificador módulo-11 calculado en Python, multiplicador 2..7 cíclico).

## Hallazgos

### HALLAZGO-EPIC11-01 (Major) — El validador de parametrización (CEPA-111) no valida la nomenclatura estándar de campos custom, solo la de los 7 campos de sistema

`validate_form_version()` (`backend/app/services/form_validator.py`) verifica: field_key duplicado, presencia/actividad/system_locked de los 7 campos obligatorios del sistema, label no vacío, field_type en el conjunto válido (o vacío), y domain_values para select requerido. **No existe ninguna regla que valide el formato del `field_key` de un campo custom** (por ejemplo, nomenclatura no estándar como `campoX1` con mayúsculas). La única validación de formato (`regex /^[a-z0-9_]+$/`) vive exclusivamente en el frontend (`frontend/src/features/config-formularios/fieldSchema.ts:14`), y el schema Pydantic del backend (`FieldDefIn.field_key: str` en `backend/app/schemas/form_config.py:15`) acepta cualquier string sin restricción. Se verificó ejecutando TC-CEPA-111-001: un borrador con campo `edad` sin `field_type` y un campo `campoX1` (nomenclatura no estándar) se publicó devolviendo únicamente el error de `edad` sin tipo — `campoX1` no generó ningún error, y la publicación se hubiera completado exitosamente si `edad` hubiera tenido tipo. Esto significa que un cliente API (o un bug de UI que no aplique el regex) puede publicar campos con cualquier nomenclatura, sin que el backend lo detecte ni bloquee.

### HALLAZGO-EPIC11-02 (Major) — No existe ningún catálogo maestro que garantice nomenclatura/dominio consistente de campos compartidos entre formularios distintos

Cada `FormDefinition`/`FormVersion`/`FieldDef` es completamente independiente por `form_key` (`backend/app/models/form_definition.py`) — no hay ninguna tabla de "campo compartido" o catálogo central de `field_key`/`domain_values` que dos formularios (p. ej. "ingresos" y "reintegro") puedan referenciar en común. Se verificó publicando el mismo campo `tipo_convenio` (mismo `field_key`, mismo dominio `["Fonasa","Isapre","Particular"]`) en dos `form_key` distintos ("ingresos" y "reintegro"): el sistema los aceptó como idénticos únicamente porque se configuraron manualmente así — no hay ningún mecanismo (validación cruzada, referencia a catálogo, alerta de discrepancia) que impida a Coordinación publicar el mismo campo con distinto dominio o tipo en dos formularios distintos. La "nomenclatura estandarizada... consistente entre módulos y reportes" (CEPA-111 BR-RN-3) depende enteramente de la disciplina manual de quien parametriza, no de un control del sistema.

### HALLAZGO-EPIC11-03 (Minor, informativo) — Los formularios dinámicos (`form_definition`/`form_version`/`field_def`) solo definen schema; no existe ninguna tabla de datos capturados ligada a ellos, y no están conectados a los endpoints de captura operativa real

El modelo de datos de CEPA-110/111 (`FormDefinition`, `FormVersion`, `FieldDef`) almacena exclusivamente la **definición** de campos (metadata), no instancias de datos capturados — no existe ninguna tabla `field_value`/`form_data` que asocie un registro real (p. ej. un ingreso concreto) a los campos de una versión de formulario. Además, `POST /api/v1/ingresos` (el endpoint real de alta de pacientes, ya cubierto en EPIC-01) no importa ni consulta `form_config`/`form_definition` en ningún punto (`grep` confirmado) — son sistemas completamente paralelos. La única superficie que sí valida datos de captura contra un formulario publicado es `POST /api/v1/pdf-extract/confirm`, que construye un mapa `field_key → value` a partir del payload y lo contrasta con los `FieldDef` de la versión publicada (requeridos y dominios) — pero esta validación tampoco persiste el dato en ninguna tabla de dominio; solo confirma y devuelve un acuse (`{"acknowledged": true}`). Esto no invalida ningún TC de esta corrida (todos los resultados esperados se cumplen usando este mecanismo de verificación, que sí ejercita la regla de negocio real), pero es relevante para entender el alcance real del módulo: es un motor de *definición y validación de schema*, no un motor de *captura dinámica* propiamente dicho — la UI operativa de Ingresos sigue usando un formulario de campos fijos hardcodeados en React (`AltaIngresoPage.tsx`), sin relación con lo que Coordinación configure en "Formularios dinámicos".

## Notas menores (no bloqueantes)

- El patrón sistémico de `rol`/`valor_anterior`/`valor_nuevo` en `null` en el log de auditoría (confirmado en EPIC-00 a EPIC-10) se repite en `form_version`, `form_version_publish_blocked`, `pdf_extract_attempt` y `pdf_extract_confirm`: `record_audit()` solo registra actor/acción/entidad/entity_id. No bloqueante para los TCs de esta épica (que exigen actor + acción + timestamp, presentes en todos los casos).
- `ConfigFormulariosPage.tsx` no bloquea la navegación por URL directa a `/config-formularios` para roles distintos de Coordinación — solo oculta el botón "Editar como nuevo borrador" (`canWrite`) y el link del sidebar (`nav.ts`, `roles: ["Coordinacion"]`). Un Administrativo/Auditor que conozca la URL puede ver la página en modo lectura (consistente con el diseño: la lectura de la versión publicada está abierta a los 3 roles, verificado con `GET /form-definitions/.../published` → 200 para los 3). No afecta el veredicto de TC-110-004 porque el TC exige "la UI no muestra el editor" (cumplido) y "API responde 403" (cumplido), no "la ruta es inaccesible".
- El validador de publicación (`validate_form_version`) actúa únicamente al momento de publicar, no al guardar un borrador — guardar un borrador con un campo de sistema removido/desactivado o con nomenclatura duplicada es intencionalmente permisivo (confirmado en TC-110-003 y TC-111-002); el enforcement real ocurre en `POST /form-definitions/{form_key}/publish/{version_id}`.
- El PDF sin capa de texto (página en blanco válida) no retorna `success=False` sino `success=True` con `fields=[]` — comportamiento distinto al de un archivo verdaderamente ilegible (no-PDF), que sí retorna `success=False` con `error_message`. Ambos casos permiten continuar con la captura manual sin bloquear el flujo, cumpliendo el espíritu de TC-112-006, aunque el mensaje visual difiere (no se muestra el bloque de "No se pudo extraer el contenido" en el caso de página en blanco, solo "0 campo(s) detectado(s)").
- La integración con SALUTEM/SAM (`backend/app/integrations/salutem/protocol.py`) es de solo lectura por diseño explícito ("D12"): la interfaz `SalutemClientProtocol` no define ningún método de escritura, y el módulo `pdf_extract.py` no la referencia en absoluto — confirma limpiamente TC-112-005 a nivel arquitectónico, sin necesidad de interceptar tráfico de red.
- RBAC de escritura (crear borrador, publicar, cargar PDF, confirmar extracción) fue verificado negativamente para los roles sin permiso en los 4 endpoints relevantes: los cuatro devuelven consistentemente `403 "No tiene permisos para esta operación"`.
- Se identificó que el schema Pydantic `FieldDefIn.field_type: str` (no-nullable) rechaza con 422 un intento de enviar `field_type: null` directamente por API — el patrón correcto para representar "campo sin tipo aún" en un borrador es `field_type: ""` (string vacío), documentado en el propio modelo ORM (`FieldDef.field_type`, comentario "Oracle trata '' como NULL"). No es un bug: es el contrato de la API tal como está documentado, simplemente requirió un ajuste en la construcción del payload de prueba.
