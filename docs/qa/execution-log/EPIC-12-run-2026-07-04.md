# Ejecución EPIC-12 — API de Integración

**Fecha:** 2026-07-04
**Alcance:** 23 TCs (CEPA-120, CEPA-121, CEPA-122, 3 historias) — piloto en ambiente local.
**Resultado:** 13 Pass, 10 Fail.

Esta es la última épica de la suite completa (EPIC-00 a EPIC-12, 402 TCs).

## Entorno

- Backend: FastAPI local (`uvicorn app.main:app --port 8000`), verificado activo (`GET /docs` → 200) antes y durante la ejecución. Proceso externo, no reiniciado.
- Metodología: "API de Integración" es un módulo puramente backend-to-backend, sin pantalla propia en el frontend (`grep -rn "integracion|imed|licencias_api"` en `frontend/src/` solo encuentra un archivo de tipos, ninguna UI de administración de integraciones/API-keys). Toda la ejecución se realizó vía `curl`/`fetch` directo contra la API, complementado con lectura de código fuente y, para CEPA-122 (IMED), ejecución de la suite de pytest existente (`backend/tests/test_imed_api.py`) para obtener evidencia real con el feature flag `IMED_ENABLED=true` sin alterar el proceso uvicorn en vivo (que corre con el flag en `false`, su valor por defecto).
- Usuarios de prueba: `cvidal` (Administrativo), `pfuentes` (Coordinacion), `mbravo` (Auditor). Login vía `POST /api/v1/auth/login`.
- Datos de prueba: paciente id=46 (RUT interno `190020045`, RUT chileno formateado `12.345.678-5` corresponde a otro paciente sembrado — "María Pérez Soto", id=63, usado para el TC de validación de DV), folio `F-2026-0046` (ingreso_id=51, 3 licencias vigentes: 15+14+30 = 59 días acumulados).
- RUT sintético con DV calculado en Python (módulo-11, multiplicador 2..7 cíclico) para pruebas del validador de RUT y de la suite pytest de IMED.
- Se descargó y auditó `GET /openapi.json` completo (88 paths) para verificar documentación, seguridad y alcance de v1.

## Hallazgos

### HALLAZGO-EPIC12-01 (Critical) — La API v1 "de integración" no está aislada: comparte namespace con toda la API interna del sistema, incluyendo recursos P1/P2 explícitamente fuera de alcance

CEPA-121 CA-3/RN-6 exige que la API v1 P0 solo exponga Pacientes, Ingresos, Fichas clínicas y Licencias, y que Fármacos/Controles/Reportes (P1/P2) no existan en v1. En la práctica, **todos** los routers de la aplicación —incluidos `registro-farmacologico`, `controles-medicos`, `reportes/*`, `auditoria/*`, `usuarios`, `agendamiento`, `alertas`, `tareas`, `form-definitions`, `pdf-extract`— están montados bajo el mismo prefijo `/api/v1` (confirmado con el listado completo de 88 paths de `openapi.json`). No existe ningún mecanismo de separación (subrouter dedicado, prefijo `/api/v1/integracion`, API Gateway, o documento OpenAPI separado) entre "el contrato de integración externa" y la API interna consumida por el propio frontend React. Un cliente externo con un JWT válido de rol Administrativo/Coordinacion puede invocar cualquier endpoint interno del sistema (crear usuarios, generar reportes de auditoría, modificar EPT/reintegro, etc.), no solo los 4 recursos declarados como el alcance P0 de la API de integración. Esto invalida el criterio central de TC-CEPA-121-007 y tiene implicancia de superficie de ataque/gobernanza para cualquier integrador externo real.

### HALLAZGO-EPIC12-02 (Major) — El endpoint de actualización de estado de Ingresos requiere el ID interno, no el folio, contradiciendo el contrato documentado en el PRD/TC

CEPA-121 CA-2 y el propio TC-CEPA-121-002 especifican `PATCH /api/v1/ingresos/{folio}/estado` (ej. `/api/v1/ingresos/2026-0001`). La implementación real (`backend/app/routers/ingresos_estado.py`) usa `ingreso_id: int` como path param — enviar el folio real (`F-2026-0046`) devuelve `422 int_parsing`. La actualización de estado sí funciona y persiste correctamente (verificado: Activo→Cerrado, con GET posterior confirmando el cambio), pero un cliente de integración externo que solo conozca el folio (el identificador de negocio, no el ID autoincremental interno de la BD) no puede usar este endpoint sin antes resolver el folio a un ID interno vía otro endpoint. Mismo patrón de inconsistencia folio-vs-id detectado también en la búsqueda de Pacientes (TC-121-001): no hay un endpoint `GET/PATCH` de Ingresos direccionable por folio.

### HALLAZGO-EPIC12-03 (Major) — El manejador de errores de la API no produce un cuerpo JSON uniforme entre códigos de estado, y la especificación OpenAPI no documenta los códigos de error reales

TC-CEPA-120-006 exige que 400/401/403/404/409/422/429/500 compartan la misma estructura de error (mismos campos: código, mensaje, detalle). En la práctica: 401/403/404 devuelven `{"detail": "<string>"}` (HTTPException estándar de FastAPI); 422 devuelve `{"detail": [{"type":..., "loc":..., "msg":..., "input":...}]}` (lista de objetos de Pydantic, estructura completamente distinta); 429 devuelve `{"error": "Rate limit exceeded: ..."}` (clave `error`, no `detail`, formato de slowapi). Un cliente de integración tendría que implementar tres parsers de error distintos según el código HTTP. Adicionalmente, ningún endpoint documenta en su `openapi.json` los códigos 401/403/404/429/500 en su bloque `responses` (solo aparecen 200/201/422, que FastAPI genera automáticamente) — contradice TC-CEPA-120-003 ("códigos de error documentados").

### HALLAZGO-EPIC12-04 (Major) — El rate limiting (429) no informa un tiempo de reintento explícito (sin header `Retry-After` ni campo numérico en el body)

Verificado enviando 65 requests en la misma ventana: las primeras 60 responden 200, las siguientes 5 responden `429` con body `{"error":"Rate limit exceeded: 60 per 1 minute"}`. La respuesta **no incluye el header `Retry-After`** (inspección completa de headers de la respuesta 429) ni ningún campo JSON con segundos/timestamp de reintento — solo un mensaje de texto libre que menciona la ventana configurada, no el tiempo restante. Contradice el resultado esperado de TC-CEPA-120-004 ("indicación del tiempo de reintento").

### HALLAZGO-EPIC12-05 (Major) — El validador de RUT (dígito verificador) existe pero falla en silencio: un RUT con DV incorrecto no produce error, solo una lista vacía

`app/util/rut.py` sí implementa `normalizar_rut()`/`RutInvalidoError` con validación de DV. Pero en `buscar_pacientes()` (`app/services/busqueda.py`), la excepción se captura con `except RutInvalidoError: pass` y la búsqueda simplemente continúa por los otros criterios (nombre/folio), terminando en `200 OK` con `[]` si no hay coincidencias — nunca en un `422`/`400` explícito indicando "RUT inválido por dígito verificador" como exige TC-CEPA-121-006. Es un diseño intencional documentado en el propio código (RN-5: "la búsqueda nunca lanza error por término inexistente"), pero significa que la API de integración no distingue entre "RUT con DV incorrecto" y "RUT válido sin resultados" — ambos casos son indistinguibles para el cliente externo.

## Notas menores (no bloqueantes)

- El patrón sistémico de `rol`/`valor_anterior`/`valor_nuevo` en `null` en el log de auditoría (confirmado en EPIC-00 a EPIC-11) se repite en todos los endpoints de esta épica (`paciente`, `ingreso`, `ficha_clinica`, `imed_payload`): `record_audit()` solo registra actor/acción/entidad/entity_id. Para IMED específicamente, el `entity_id` registrado es el ID interno autoincremental del `imed_payload`, no el folio del paciente — un auditor debe hacer un join manual (consultar la tabla `imed_payload` por ese id) para saber a qué folio corresponde una entrada de auditoría IMED (afecta TC-CEPA-122-004).
- No existe el concepto de "scope IMED" separado del rol de usuario mencionado en TC-CEPA-122-007/122-005: la autorización de los endpoints IMED usa el mismo `require_role("Administrativo", "Coordinacion")` que el resto del sistema. El resultado observable (403 para un token sin ese rol, ej. Auditor) coincide con lo esperado por el TC, pero el mecanismo es RBAC por rol, no un scope de token dedicado a integraciones.
- El recurso Pacientes de la API de integración (`GET /api/v1/pacientes/buscar?q=...`) no coincide con la forma de invocación literal de varios TCs (`GET /api/v1/pacientes?rut=...`, `?nombre=...`, `?folio=...`): el filtrado real es un único parámetro `q` de búsqueda combinada (RUT/nombre/folio), no query params independientes. La funcionalidad subyacente de búsqueda multi-criterio sí funciona (verificado con los 3 criterios), documentado como discrepancia de contrato, no como ausencia de funcionalidad.
- No existe un recurso `/api/v2/*` de negocio real (solo `/api/v2/health`), por lo que TC-CEPA-120-005 (coexistencia de contratos v1/v2 con cambios incompatibles) no pudo verificarse contra un caso real de versionado de recurso — solo se confirmó que v1 sigue respondiendo con normalidad mientras existe un v2 (aunque este último sea solo un healthcheck).
- La integración SALUTEM/SAM (`backend/app/integrations/salutem/protocol.py`, `client.py`) es de solo lectura por diseño explícito y verificable en runtime: `SalutemClientProtocol` únicamente define `get_paciente`, `get_ficha_clinica`, `get_licencias` (confirmado por inspección de `dir()` del cliente activo, cero métodos de escritura). El cliente real es un stub (`SalutemStubClient`, PA2 pendiente de confirmar API real) que devuelve `None`/`[]`; el diseño arquitectónico (Protocol sin escritura) es la garantía real de D12, no el comportamiento del stub.
- La suite de pytest `backend/tests/test_imed_api.py` (7 tests) ya cubre exactamente los escenarios de TC-CEPA-122-001/002/003/006/007 con `IMED_ENABLED=true` vía `monkeypatch`, aislada de la BD/proceso en vivo. Se ejecutó (`pytest tests/test_imed_api.py -v`) obteniendo 7/7 passed, usado como evidencia primaria para esos TCs dado que el entorno vivo tiene el flag en `false` (valor por defecto, sin override en `.env`) y no debía reiniciarse el proceso.
- No hay ninguna pantalla de administración de integraciones/API-keys en el frontend; toda la épica se validó backend-to-backend.
