## Hallazgos

### HALLAZGO-EPIC04-01 (Major) — No existe pre-llenado de datos al ingresar un RUT existente

`NuevoCasoReintegroDialog.tsx` no tiene ninguna lógica de búsqueda/prefill al escribir el RUT (confirmado en código: no hay `onBlur`, debounce ni llamada a `buscarPacientes` desde este formulario). Se verificó en vivo: al ingresar el RUT de un paciente existente (con nombre, sexo M y región "Región de Ñuble" ya registrados), los campos Nombre, Sexo y Región permanecieron vacíos/con su valor por defecto ("Femenino"). El Administrativo debe volver a tipear manualmente todos los datos sociodemográficos aunque el paciente ya exista en el sistema. Afecta a TC-CEPA-040-001.

### HALLAZGO-EPIC04-02 (Major) — El caso de reintegro no es visible desde el módulo de Ingresos

`PatientSheet.tsx` (ficha de paciente del módulo de Ingresos) no contiene ninguna referencia a "reintegro" — no hay tab, sección ni indicador que muestre si un folio tiene un caso de reintegro asociado. El caso sí es descubrible desde el propio módulo de Seguimiento de Reintegro (buscando al paciente ahí), pero la integración cruzada descrita en TC-CEPA-040-002 ("desde el módulo de Ingresos el folio muestra el caso de reintegro asociado") no existe.

### HALLAZGO-EPIC04-03 (Major) — Mensajes de error genéricos ocultan el detalle específico del backend

Igual patrón que en EPIC-03: `frontend/src/features/reintegro/api.ts` traduce cualquier 422 a un texto fijo genérico ("Datos inválidos. Revisa los campos.", "Datos inválidos. Revisa fechas y campos de la RECA.", "Datos de cierre inválidos..."), descartando el `detail` específico que el backend sí calcula correctamente (p. ej. `"RUT inválido: '12.345.678-0'"`). El usuario nunca ve el mensaje preciso ni la ubicación del error junto al campo. Afecta a TC-CEPA-040-003 y, de forma transversal, a la experiencia de cualquier TC que dependa de leer el mensaje de error en la UI.

### HALLAZGO-EPIC04-04 (Major) — No existe mecanismo de folio manual/histórico en el alta de reintegro

El formulario y el schema (`CasoReintegroCreate`) no tienen ningún campo de folio — el caso se vincula únicamente al `ingreso_id` resuelto automáticamente desde la búsqueda de paciente (toma el primer ingreso, mismo patrón que EPT/Fármacos). No hay forma de "activar folio manual" ni de vincular explícitamente un folio histórico distinto al ingreso resuelto por defecto. Afecta a TC-CEPA-040-005 y, en la práctica, hace inalcanzable el escenario de reingreso a un folio antiguo específico cuando el paciente tiene múltiples ingresos.

### HALLAZGO-EPIC04-05 (Major) — `comuna` es opcional pese a ser sociodemográfico obligatorio según la especificación

El modelo (`comuna: Mapped[str | None] = ... nullable=True`) y el schema (`CasoReintegroCreate.comuna: str | None = None`) tratan la comuna como opcional. Se confirmó creando un caso sin `comuna` → `201 Created` sin error. Esto contradice directamente TC-CEPA-040-007, que exige que sexo, edad/tramo etario, región **y comuna** sean obligatorios para alimentar los filtros del dashboard.

### HALLAZGO-EPIC04-06 (Major) — El log de auditoría de Reintegro nunca registra valores modificados

Mismo patrón sistémico de EPIC-00/01/02/03: los cuatro endpoints de escritura (`caso_reintegro` crear/editar, `reca` crear/editar, `cierre`) llaman a `record_audit()` sin `valor_anterior`/`valor_nuevo`/`rol`. El log captura correctamente actor y fecha/hora, pero nunca qué cambió — afecta a TC-CEPA-040-008, TC-CEPA-041-008 y TC-CEPA-042-009 (esta última pide explícitamente que se registre "el cambio de estado").

### HALLAZGO-EPIC04-07 (Major) — Una RECA "extra" con número distinto puede crearse silenciosamente para un caso que ya tiene una

El modelo declara la relación `CasoReintegro.reca` como uno-a-uno (`uselist=False`) y su docstring afirma "Una RECA por caso de reintegro", pero `crear_reca()` (`backend/app/services/reintegro.py:177-225`) solo valida que el **número** de RECA no se repita dentro del caso — no valida que el caso ya tenga una RECA registrada. Se reprodujo: al caso 37 (ya con RECA N° 2026-0042) se le agregó una segunda RECA con número distinto (2026-9999) y la API respondió `201 Created` sin error. El `GET /reca` posterior solo devuelve la primera RECA creada (id 27) — la segunda (id 28) queda huérfana e inaccesible por API, un caso silencioso de datos inconsistentes. **Mitigante:** la UI normal no expone esta ruta (una vez que existe una RECA, `RecaPanel` solo ofrece "Editar RECA", que usa `PATCH`, no `POST`), por lo que el bug solo es alcanzable llamando la API directamente, no a través del flujo estándar de un usuario.

### HALLAZGO-EPIC04-08 (Major) — No existe reporte de auditoría/contraparte que exponga `remitido_isl`

No se encontró ningún endpoint de reporte (`reporte_*.py`) que liste casos de reintegro remitidos al ISL. El campo `remitido_isl` se guarda y se lee correctamente en el detalle del caso, pero TC-CEPA-042-008 pide específicamente que el caso "aparezca disponible en el reporte de auditoría/contraparte" — esa superficie no existe.

## Notas menores (no bloqueantes)

- El catálogo `TipoDerivacion` reutilizado de EPIC-01 usa "Convenio U.Clinica" sin tilde (mismo detalle cosmético ya documentado en EPIC-01).
- No existe un campo `folio` propio en `caso_reintegro` — se accede al folio solo indirectamente vía `ingreso_id → ingreso.folio`; funcionalmente el vínculo es correcto pero el modelo de datos de TC-CEPA-040-010 no lo expone como columna propia.
- La ambigüedad entre las columnas "REINTEGRO" y "ESTADO" de la planilla original (TC-CEPA-042-010) parece resolverse en un único campo `estado_reintegro` — razonable, pero no verificable con certeza sin el Excel de origen.
- `CierreReintegroUpdate` no usa `exclude_unset` (a diferencia de `CasoReintegroUpdate`), por lo que un PATCH de cierre que no incluya explícitamente un campo lo resetea a su default (`False`/`None`) en vez de preservarlo. En la práctica no es observable desde la UI porque `CierreDialog` siempre precarga el formulario con los valores actuales del caso antes de permitir editar, pero sí sería un riesgo para cualquier integración que llame la API directamente con payloads parciales.
