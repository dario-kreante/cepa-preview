## Hallazgos

### HALLAZGO-EPIC10-01 (Critical) — No existe ninguna acción en la UI para marcar una alerta como leída o resuelta

El hook `useActualizarAlerta()` (`frontend/src/features/alertas/hooks.ts:13-22`) y la función `actualizarAlerta()` (`frontend/src/features/alertas/api.ts:23-34`) que envuelven `PATCH /api/v1/alertas/{id}` existen y están completos, pero **no se usan en ningún componente del frontend** (`grep` de `useActualizarAlerta|actualizarAlerta` sobre todo `frontend/src/` solo encuentra los dos archivos que los definen). `AlertsPanel.tsx` (`AlertItem`, líneas 116-144) únicamente ofrece `onClick` para navegar al módulo de origen (`routeForCaso`) — no hay botón, menú contextual, swipe ni ningún otro control para cambiar el estado de una alerta. El backend (`PATCH /api/v1/alertas/{id}`, transiciones pendiente→leída→resuelta) funciona correctamente y fue verificado exhaustivamente por API (ver TC-101-004), pero un usuario real de la aplicación no tiene ninguna forma de marcar una alerta como atendida sin usar la API directamente. Esto invalida el requisito central de CA-4 de CEPA-101 ("al marcar una alerta como leída o resuelta").

### HALLAZGO-EPIC10-02 (Critical) — No existe ninguna página ni acción de UI para el módulo de tareas pendientes (CEPA-103)

El router `backend/app/routers/tareas.py` (`GET/POST /api/v1/tareas`, `PATCH /api/v1/tareas/{id}`) está completo y correctamente implementado (RBAC, transición a completada con `completada_por`/`completada_en`), y las tareas se listan mezcladas con las alertas dentro de `AlertsPanel.tsx` (componente `TareaItem`, líneas 151-187) — pero **solo como lectura**: el `onClick` de `TareaItem` navega al caso de origen igual que una alerta, y no existe ningún botón "Completar tarea" en el panel. No existe además ninguna página dedicada de "Tareas pendientes" en el frontend (`find` sobre `frontend/src` de archivos con "tarea" en el nombre solo encuentra `AlertsPanel.test.tsx`/`hooks.ts`/`api.ts` de alertas; no hay `TareasPage.tsx` ni entrada de navegación en el sidebar) — no hay tampoco función `actualizarTarea`/`completarTarea` en `frontend/src/features/alertas/api.ts`, a diferencia de las alertas donde al menos el hook huérfano existe. Esto invalida CA-1 (vista dedicada por perfil/asignación), CA-2 (completar tarea) y CA-4 (vista de supervisión de Coordinación) de CEPA-103 en su totalidad desde la superficie de usuario; la lógica de negocio del backend sí es correcta y fue verificada por API.

### HALLAZGO-EPIC10-03 (Major) — El job de alertas no tiene ningún planificador (scheduler) real; solo se ejecuta bajo demanda vía API

No existe en el código ningún `BackgroundScheduler`, `cron`, tarea periódica o proceso equivalente para `ejecutar_job_alertas()` (`grep` de "scheduler|cron|APScheduler|celery" sobre `backend/app` solo encuentra `agendamiento/scheduler.py`, que es un módulo distinto de EPIC-06 sin relación con alertas). El único punto de entrada es `POST /api/v1/alertas/ejecutar-job`, que debe ser invocado manualmente (o por un cron externo al proceso de la aplicación, no verificable desde este ambiente). No hay evidencia de una frecuencia configurable, ventana de mantenimiento nocturna respetada, ni historial/log de ejecuciones del job distinto del log de auditoría genérico (`entity_id="job:N"`, que solo registra cuántas alertas se generaron, no cuándo debía ejecutarse ni si se saltó una corrida). Esto invalida CEPA-100 BR-RN-2 (TC-100-009) en su totalidad — la "programación en días hábiles con frecuencia configurable" no existe como funcionalidad del sistema, es una responsabilidad delegada a infraestructura externa no presente en este ambiente.

### HALLAZGO-EPIC10-04 (Major) — Las ventanas de aviso están hardcodeadas en código (`VENTANAS_DEFAULT`); no son parametrizables sin despliegue

`VENTANAS_DEFAULT` (`backend/app/services/alertas.py:177-185`) es un diccionario Python constante definido en el módulo de servicio. No existe ningún modelo, tabla, endpoint ni UI para leer o modificar los valores de ventana en runtime (`grep` de "ventanas.*alertas|VentanaAlerta|config.*alerta" sobre `backend/app` no encuentra ningún endpoint de configuración — a diferencia de `ConfigVentanaProceso` de EPIC-09, que es un módulo de metadatos de columnas no relacionado). Los valores por defecto observados coinciden con lo documentado (licencia=3 días hábiles, EPT/ISL=5 días hábiles, receta=5 días calendario, ODA=7 días calendario, control médico=7 días calendario, consentimiento=30 días calendario), pero cambiar cualquiera de ellos requiere modificar el código fuente y desplegar una nueva versión del backend. Esto contradice explícitamente CEPA-100 BR-RN-3 (TC-100-010: "el cambio de parámetro surte efecto sin despliegue").

### HALLAZGO-EPIC10-05 (Major) — No existe ningún mecanismo de trazabilidad histórica de "0% de vencimientos sin alerta previa" (OU4)

El sistema no mantiene ningún registro histórico que permita auditar, para un plazo ya vencido, si efectivamente existió una alerta generada antes de su vencimiento — solo existe el estado actual de la tabla `alerta_notif` (con su `generada_en`). Si una alerta fue generada y luego resuelta o si el plazo cambió, no hay forma de reconstruir retrospectivamente "este plazo tuvo alerta antes de vencer" a nivel de reporte/KPI — la única evidencia es indirecta, cruzando manualmente `AlertaNotif.generada_en` contra el plazo original en la tabla de dominio. No existe ningún endpoint de tipo `GET /alertas/cobertura` o similar. Esto invalida la verificación operativa de CEPA-100 OU4 (TC-100-008) como métrica medible del sistema; la propiedad puede cumplirse de facto (el motor evalúa todos los plazos en cada corrida) pero no es auditable ni reportable sin consulta manual a la BD.

### HALLAZGO-EPIC10-06 (Medium) — El SMTP institucional no está configurado en este ambiente; el envío real de correos no pudo verificarse end-to-end

`Settings.smtp_host` (`backend/app/config.py:41`) es `""` por defecto y no hay override en el ambiente QA local — confirmado con `get_settings().smtp_host == ''`. El endpoint `POST /alertas/enviar-correos` se comporta exactamente como especifica el diseño (DD-C): retorna `200` con `alertas_generadas=0` y `omitidas=N` (76 en la corrida) sin lanzar excepción ni bloquear el sistema. La lógica de degradación controlada (`enviar_alerta()` en `email_sender.py`, captura `ConnectionError` y devuelve `False`) fue revisada en código y es correcta, pero no pudo ejercitarse con un servidor SMTP real ni verificarse la recepción de un correo en una bandeja real. No es un defecto del sistema — es una limitación del ambiente de pruebas.

## Notas menores (no bloqueantes)

- El patrón sistémico de `rol`/`valor_anterior`/`valor_nuevo` en `null` en el log de auditoría (confirmado en EPIC-00 a EPIC-09) se repite en `alerta_notif` y `tarea_item`: `record_audit()` solo registra actor/acción/entidad/entity_id, sin el detalle de valores. No bloqueante para los TCs de esta épica, que solo exigen actor + fecha/hora, presentes en ambos casos.
- El catálogo de roles (`Rol = Literal["Coordinacion", "Administrativo", "Auditor"]`, `backend/app/schemas/usuario.py:6`) es un tipo cerrado real a nivel de aplicación: se verificó con `POST /usuarios` que un intento de crear un usuario con `rol="Clinico"` es rechazado con HTTP 422 y mensaje explícito `"Input should be 'Coordinacion', 'Administrativo' or 'Auditor'"` — la mejor evidencia de "D1: no existe perfil Clínico" vista en las 10 épicas ejecutadas hasta ahora.
- No existe ningún canal de notificación WhatsApp en el código (`grep` de "whatsapp|WABA" sobre todo el backend y frontend no arroja resultados) — confirma limpiamente TC-102-006 sin necesidad de un hallazgo dedicado, es la ausencia esperada y documentada (P2, sin WABA).
- La idempotencia del job (clave `(caso_id, tipo, plazo_objetivo)`) se verificó de forma extremadamente sólida: tras generar 8 alertas nuevas del set de control, una segunda ejecución inmediata del job devolvió `alertas_generadas=0` sin ningún duplicado.
- El destinatario de la alerta (`_resolver_usuario`, `Ingreso.profesional_id`) se comporta exactamente como documenta la nota abierta PA: 27 de las 79 alertas totales en BD tienen `usuario_id=null` (ingresos sin profesional asignado) — visibles solo para Coordinación/Auditor (panel global), invisibles para cualquier Administrativo específico. Esto no es un bug, es el comportamiento de diseño documentado, pero deja en evidencia que una fracción significativa (~34%) de las alertas reales de este ambiente no llegan a ningún responsable operativo concreto.
- RBAC de escritura (job, PATCH de alertas, POST/PATCH de tareas) fue verificado negativamente con el rol Auditor en los tres endpoints: los tres devuelven `403 "No tiene permisos para esta operación"` de forma consistente.
- El estado vacío (usuario sin alertas ni tareas, `qa_epic10_empty`) se verificó visualmente en la UI real: mensaje "Sin alertas en esta categoría", sin badge numérico en el header, sin errores en consola, resto de la aplicación (Dashboard, navegación) operativo con normalidad.
